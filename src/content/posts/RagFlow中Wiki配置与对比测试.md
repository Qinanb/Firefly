在 RAGFlow 新版本中，**Wiki** 属于**知识编译（Knowledge Compilation）体系下的知识库级工件（Knowledge-base-level Artifact），而自定义文档解析 Pipeline（Ingestion Pipeline）** 则是基于 Agent 画布构建的可视化 ETL 流程。

---

### 一、新版本 Wiki 的设置与生成流程

Wiki 是通过对知识库中文档进行深度编译并提炼后，在整个知识库层级聚合生成的结构化知识页面。

1. **配置编译模板（Compilation Template）**
* 进入 **Knowledge Compilation（知识编译）** 菜单
可以选择以下模板：

| 模板                               | 作用                                         |
| -------------------------------- | ------------------------------------------ |
| Graph（知识图谱）                      | 从所有文档中提取实体 + 实体之间的关系，构建一张网状知识图谱（Graph‑RAG） |
| Mindmap（思维导图）                    | 提炼知识库主题‑子主题发散层级，生成树状思维导图结构                 |
| PageIndex（目录导航索引，旧名 TOC‑Enhance） | 解析文档自带的标题、章节目录层级，生成文档原生目录树；无向量检索也可导航       |
| Timeline（时间线）                    | 自动识别文档内所有时间点‑事件，按时间先后顺序生成时序索引              |
| Tree（通用层级树）                      | 让 LLM 自主归纳全文内容，生成一棵通用逻辑层级树；不受原文档标题约束       |
| Wiki（百科式知识库）                     | 把知识库内容提炼成词条‑释义的百科全书结构，自动生成词条条目             |

| Wiki有两个模式分别为：                                       |      |
| ------------------------------------------------------------ | ---- |
| **实体模式：** 每个实体或概念对应一个Wiki页面                |      |
| **主题模式：** 让LLM按主题将相关实体或概念组合到同一个Wiki页面 |      |

* 新建或选择内置的编译模板，配置实体提取、结构归纳与 Wiki 页面生成规则。

| 面板标签                   | 图谱角色           | 核心用途                    | 产出物                                 |
| ---------------------- | -------------- | ----------------------- | ----------------------------------- |
| Entity specification   | Node 节点（具象对象）  | 限定可抽取的实物对象范围，减少幻觉       | person、org、system、equipment 等实体     |
| Relation specification | Edge 边（连接线）    | 限定实体之间允许生成的关系类型         | owns /part_of/uses /regulates 等谓词关系 |
| Claim specification    | Evidence 事实证据  | 为图谱节点绑定原文证据片段，增强多跳问答可靠性 | 原文事实快照，推理溯源防幻觉                      |
| Concept specification  | Concept 抽象概念节点 | 提取业务术语、流程、主题概念，补充知识库语义  | 运维流程、业务规范一类抽象词条                     |

**蓝图：** 把“原始资料如何加工成 Wiki 内容”预先定义好，之后让系统按这套规则自动生成。
系统自带以下模板：

| 模板             | 作用         |
| -------------- | ---------- |
| Brand          | 品牌相关       |
| Engineer       | 工程、研发、技术流程 |
| General        | 通用场景       |
| Market         | 市场营销       |
| Product        | 产品设计、产品管理  |
| User interview | 用户访谈       |
| Custom         | 自定义蓝图      |

这个分类通常不会改变 RagFlow 算子本身的执行逻辑，也不会自动完成 Wiki 编译。真正决定功能的是蓝图内部连接的节点、算子、输入和输出。


2. **在 Ingestion Pipeline 中引入编译算子**

* 在 Agent 的 Ingestion Pipeline 画布中，添加 `CompilerOperator` 节点，并关联刚才配置的 Compilation Template。


3. **知识库绑定 Pipeline 并解析**
* 进入目标 **Dataset / Knowledge Base**，在解析配置中将方法设置为该 Ingestion Pipeline。
* 上传文档并启动解析，系统会依次完成文档解析、切分和单文档编译。


4. **生成与维护 Wiki**
* 解析完成后，进入知识库详情页，点击左侧边栏的 **Artifacts（工件）**。
* 右上角工件类型下拉列表中选择 **Wiki**，点击 **Generate（生成）** 触发知识库级别的 Wiki 聚合生成。
* **增量更新**：当知识库新增或删除文档时，页面会显示待同步提示，点击 **Update** 按钮即可完成增量更新。

### 二、文档解析 Pipeline 应配置的核心节点

自定义解析 Pipeline 采用线性流水线设计，覆盖 **输入 -> 解析 -> 切分 -> 增强/编译 -> 索引** 完整链路：

| 节点类型     | 节点名称                        | 核心作用与配置建议                                                                               |
| -------- | --------------------------- | --------------------------------------------------------------------------------------- |
| **入口**   | **Begin / File**            | 流水线起点，接收知识库上传的原始文件输入。                                                                   |
| **解析器**  | **Parser**                  | 将各类非结构化文档转化为结构化文本。可针对不同格式配置引擎（如 PDF 选 DeepDoc/MinerU/VLM，图片配 OCR，音频配 ASR）。              |
| **分块器**  | **Title Chunker**           | 基于文档目录和标题层级（H1-H6）进行结构化切分，保留天然语义边界。                                                     |
| **分块器**  | **Token Chunker**           | 控制最大分块大小（如 512 Tokens）、重叠率（Overlap 建议 10%~20%）和自定义分隔符（`\n` 等）。                          |
| **语义增强** | **Transformer / Extractor** | 调用 LLM 对 Chunk 提取摘要（Summary）、关键词（Keywords）、问答对（Q&A pairs）或元数据，弥合检索语义鸿沟。                 |
| **知识编译** | **Compiler Operator**       | 绑定 Compilation Template，生成实体关系、思维导图及用于 Wiki 生成的中间编译数据。                                  |
| **索引器**  | **Indexer**                 | 流水线终点。配置写入数据库（Infinity/Elasticsearch）的模式（全文 Full-text、向量 Embedding 或混合 Hybrid）及文件名检索权重。 |

### 三、测试对比

|                  | 内置                                 | pipeline（Wiki）                                             | 注                                                           |
| ---------------- | ------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 支持的文档格式   | PDF、表格、md、txt、html、docx、pptx | PDF、表格、md、txt、html、docx、pptx                         | 虽然两种解析方式支持的文件类型相同，但是**pipeline对QA问答对的效果很差**，并且只支持按字符或者标题进行切分。 |
| 文件解析时间     | 3m的PDF文件大约需要23min左右         | 对于3m的PDF文件大约需要20min左右，时间主要花费在PDF的parser过程；生成wiki需要15min左右。总耗时在35min |                                                              |
| 知识库检索时间   | 简单问题：2s复杂问题：2s             | 简单问题：2s  复杂问题：2s                                   | 在相同问题、相同模型的情况下，虽然二者检索时间相差不大，但是内置方法稍快（0.3s左右） |
| 输出质量         | 6.5/10                               | 8/10                                                         | 对于简单问题（如”什么是十严禁十必须“）二者检索结果相差不大；对于复杂问题（涉及复杂关联）pipeline的效果要比原始方式评分更高（这里使用GPT5.6对两种方式的回答效果进行打分） |
| 是否输出Wiki索引 |                                      | **RAGFlow 原生不会把图谱节点 ID 输出到回答文本中**。图谱仅用于召回相关文档切片；召回完成后，后续引用溯源依然绑定到被召回的文本 Chunk。 |                                                              |

[^备注]: 智能体检索测试时使用的模型：问题重写（qwen3-14b）、知识检索中Rerank模型（qwen3-rerank）、知识库回答（kimi-k2.5）; pipeline编译器模型（qwen3-14b）
